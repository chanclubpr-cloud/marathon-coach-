## ส่วนที่ 1 — แนวการโค้ชที่ถอดได้จากแอป

| องค์ประกอบ | สิ่งที่แอปกำหนด |
|---|---|
| Periodization | BASE (10–12 wk) → BUILD (8–10) → PEAK (6–8) → TAPER (2–3) |
| BASE | Easy 3 วัน, Fastlek 1:1, Long run เพิ่มช้าๆ, Stride ทุกวัน — Volume 30–50 km |
| BUILD | Interval 400–1000 m, Long run + Moderate ช่วงท้าย, Fastlek 2:1 — 45–65 km |
| PEAK | Tempo/Interval 1000–2000 m, Long run + Marathon Pace ช่วงท้าย — 55–75 km |
| TAPER | Long run สั้นลง 40% — 20–35 km |
| Zone | Speed Test 12 นาที / 3 นาที / 20 วินาที → FatMax, LT1, Moderate, LT2, MP |
| Progression | +8%/สัปดาห์, Down week ทุกสัปดาห์ที่ 4 (ลด 30%) |
| Guard rail | วันหนักห้ามติดกัน |

## ส่วนที่ 2 — ความรู้ของ AI เทียบกับแนวที่สอน

### 2.1 ข้อค้นพบหลัก: AI "ไม่รู้จัก" แนวของคุณ

System prompt ของ AI คือ
`"ใช้หลักการ Maffetone, Daniels, Seiler 80/20, Norwegian Method"`

ปัญหา:
1. **เป็นสำนักที่ขัดกันเอง** — Maffetone ใช้ HR = 180 − อายุ และแทบไม่มี Speed work ในช่วงฐาน ส่วน Norwegian ใช้ Double threshold ที่ควบคุมด้วย Lactate ส่วน Daniels ใช้ VDOT AI จะเลือกผสมเอาเองแบบสุ่ม ผลคือคำแนะนำแต่ละครั้ง "ไม่คงเส้นคงวา" (inconsistency)
2. **ไม่มีแนวของคุณใน prompt เลย** — AI ไม่ได้รับ: ตาราง Session ของแต่ละ Phase, Fastlek 1:1 vs 2:1, Long Run Guide (14–35 km), กฎ Down week ทุก 4 สัปดาห์, Long run สูงสุดที่ตั้งไว้ (`max_long_run`), จำนวนวันที่เหลือก่อนแข่ง
3. **ส่ง Zone ให้ AI ไม่ครบ** — ส่งแค่ Easy, LT2, MP ไม่ส่ง Moderate และ VO2max
4. **Zone ที่ส่งไปเป็นค่าผิด** (ดูข้อ 3.1) — AI จึงวิเคราะห์ Pace บนตัวเลขที่ไม่มีความหมาย

> เปรียบเทียบเชิงคลินิก: เหมือนให้แพทย์เวรอ่าน EKG โดยไม่บอกว่าหน่วยงานใช้ CPG ฉบับไหน — เขาตอบได้ แต่ตอบตามตำราที่ตัวเองถนัด ไม่ใช่ตาม Protocol ของหน่วย

### 2.2 ตัวอย่าง JSON ใน prompt "สอนผิด" ให้ AI

AI มีแนวโน้มลอกตัวอย่าง (anchoring bias) ตัวอย่างใน `runAI` คือ
```
พฤหัส: Fastlek 1/1 ×18
ศุกร์:  Long run 18 km Easy
```
= **วันหนัก 2 วันติดกัน** ซึ่งขัดกับ Guard Rail ของแอปเอง และ Long run 18 km ถูก hard-code จึงมักได้ 18 km ทุกครั้งไม่ว่าผู้ใช้อยู่ Phase ไหน

ส่วน Plan Validator ตัวอย่างคือ `"verdict":"ผ่าน","score":85` และทุก check `pass:true` → AI เอนเอียงไปทาง "ผ่าน" (positive bias)

### 2.3 ให้ AI ตัดสินสิ่งที่ควรคำนวณด้วยสูตร

- **80/20** — AI ไม่ได้รับเวลา/Pace ของแต่ละ Session จึง "เดา" สัดส่วน ควรคำนวณในแอปจากนาทีจริงแล้วส่งตัวเลขให้ AI อธิบาย
- **Phase ถัดไป** — AI เลือกเองได้ ทั้งที่ควรคำนวณจากวันแข่งถอยหลัง (เช่น เหลือ 3 สัปดาห์ = TAPER แน่นอน)
- **Down week** — แอปมีกฎ `weekNum % 4 === 0` แต่ AI ไม่รู้

หลักการ: **"Rule-based ทำสิ่งที่วัดได้ / AI ทำสิ่งที่ต้องตีความ"** (เช่น อ่าน feel, notes, ความเหนื่อยสะสม)

### 2.4 ขาด Safety layer (สำคัญมากเมื่อให้เพื่อนใช้)

ไม่มีคำสั่งให้ AI ตรวจสัญญาณอันตรายจากช่อง "ความรู้สึก/โน้ต" เช่น
- เจ็บแน่นหน้าอก, ใจสั่น, หน้ามืด/หมดสติขณะวิ่ง → หยุดซ้อม พบแพทย์
- ปวดจุดเดิมต่อเนื่อง / ปวดกระดูก (Stress fracture), ไข้/ไม่สบาย (Neck check rule)
- HR ขณะ Easy สูงผิดปกติหลายวัน, RPE สูงต่อเนื่อง → สัญญาณ Overreaching

และควรมีข้อความว่า AI ไม่ใช่การวินิจฉัยทางการแพทย์

### 2.5 ฟีเจอร์ที่ "เขียนไว้แต่ไม่ทำงาน"

- `valResult.dayFeedback` ถูกนำไปแสดงในหน้า Plan แต่ prompt ไม่เคยขอ field นี้ → ไม่เคยแสดง

## ส่วนที่ 3 — Bug ที่ทดสอบยืนยันแล้ว

### 3.1 🔴 Zone Calculator แสดงค่าผิดหน่วย (สำคัญที่สุด)

สูตรคำนวณ Pace เป็น **วินาที/km** แต่ฟังก์ชันแสดงผล `dp()` ตีความเป็น **นาที/km**
ทดสอบด้วยค่าตัวอย่างในแอป (12 นาที 2580 m, 3 นาที 674 m, 20 วิ 117 m):

| Zone | แอปแสดง | ค่าที่ควรเป็น |
|---|---|---|
| Marathon Pace | **326:26** | 5:26 /km |
| LT2 | **299:58 – 274:00** | 5:00 – 4:34 |
| Easy/LT1 | **451:32 – 347:02** | 7:32 – 5:47 |

ค่าผิดเหล่านี้ถูกบันทึกลง DB และส่งให้ AI + Volume Calculator ใช้ต่อ
(เพิ่มเติม: ฟังก์ชันปัดเศษได้ "4:60" แทน "5:00")

### 3.2 🟠 การเดาประเภท Session (`guessType`) ผิด

| ข้อความแผน | แอปเดา | ที่ถูก |
|---|---|---|
| `Easy 60 + Stride 100×3` (ตัวอย่างในแอปเอง) | interval | easy |
| `Fastlek 1/1 ×18` (ตัวอย่างใน AI prompt) | interval | fastlek |
| `Tempo 8 km` | other | tempo |

ผลกระทบ: Guard Rail เตือนผิด, Tempo ไม่ถูกนับเป็นวันหนัก, สถิติผิด

### 3.3 🟡 ข้อสังเกตเชิงสรีรวิทยาของสูตร Zone (ขอให้ยืนยันกับแนวที่สอน)

1. **ช่วง Easy เร็วกว่า LT1** — ขอบเร็วของ Easy = LT1 × 0.94 (5:47) ขณะ LT1 = 6:09 → ผู้ใช้วิ่ง Easy เกิน LT1 ได้ ขัดกับหลัก 80/20 ที่ Easy ต้อง "ต่ำกว่า LT1"
2. **Zone ซ้อนทับ/มีช่องว่าง** — Moderate (5:32–4:54) ซ้อนกับ LT2 (5:00–4:34) และช่วง 5:47–5:32 ไม่อยู่ใน Zone ใด
3. **LT1 = LT2 × 1.28** — ห่างจาก LT2 ถึง 28% ขณะที่ในงานวิจัยส่วนใหญ่ LT1 ช้ากว่า LT2 ราว 10–20%
4. **VO2max zone มาจาก 20 วินาที All-out** — 20 วินาทีสะท้อนระบบ ATP-PCr (Speed/Neuromuscular) ไม่ใช่ VO2max ซึ่งใกล้กับ Pace 3–6 นาทีมากกว่า
5. **ค่า 12 นาที (Cooper)** ใช้คำนวณ VO2max แต่ไม่ได้ใช้กำหนด Zone; **ส่วนสูง** เก็บแต่ไม่ได้ใช้; **%Body fat ปรับ FatMax** ยังไม่มีหลักฐานรองรับชัดเจน

> ถ้าเป็นแนวที่คุณตั้งใจและมีเหตุผลรองรับ ให้เขียนเหตุผลลงเอกสารแนวการสอน แล้ว AI จะอธิบายให้ผู้ใช้ได้ถูกต้อง

### 3.4 🟡 Volume Guide ใช้ช่วงตายตัว
- BASE เริ่มที่ 30 km เสมอ — เพื่อนที่วิ่งอยู่ 15 km/สัปดาห์จะถูกแนะนำให้กระโดดเท่าตัว (เสี่ยงบาดเจ็บ)
- TAPER ควรคิดเป็น % ของ Peak volume ไม่ใช่ 20–35 km ตายตัว
- ถ้าสัปดาห์ก่อนเป็น Down week สัปดาห์ถัดไปจะคิด +8% จากค่าที่ลดแล้ว

## ส่วนที่ 4 — ความพร้อมก่อนให้เพื่อนใช้

### 🔴 ต้องแก้ก่อนแชร์ (Blocker)

| # | ปัญหา | ความเสี่ยง | วิธีแก้ |
|---|---|---|---|
| 1 | **API key ของ Anthropic อยู่ในเบราว์เซอร์** (`VITE_ANTHROPIC_API_KEY`) | ใครเปิดเว็บก็ดู key ได้ใน DevTools → เอาไปใช้ เงินคุณถูกเรียกเก็บ | ย้ายการเรียก AI ไป **Supabase Edge Function** (เก็บ key เป็น Secret) |
| 2 | **RLS เปิดให้ทุกคนอ่าน/เขียนทุกแถว** (`using (true)`) | ใครก็อ่าน/ลบข้อมูลของเพื่อนทุกคนได้ รวมน้ำหนัก, %ไขมัน, HR = **ข้อมูลสุขภาพ (ข้อมูลอ่อนไหว ตาม PDPA ม.26)** | Policy `using (auth.uid()::text = user_id)` ทุกตาราง |
| 3 | **Schema ไม่ตรงกับโค้ด** | โค้ดใช้ตาราง `zones` และคอลัมน์ `display_name`, `avatar_url` ที่ไม่มีใน `supabase-schema.sql` → ติดตั้งใหม่แล้วพัง | อัปเดต schema ให้ครบ + ใช้ migration |
| 4 | **ไม่มี Pre-participation screening** | เพื่อนที่มีโรคหัวใจ/ความดัน/เบาหวานแฝงอาจได้โปรแกรมหนัก | เพิ่มแบบคัดกรอง **PAR-Q+** ตอนสมัคร (สอดคล้องแนว ACSM) + ข้อความยินยอม/ข้อจำกัดความรับผิด |

### 🟠 ควรแก้ (ประสิทธิภาพ/ความถูกต้อง)

5. **การบันทึกทุก 1.5 วินาทียิง 14 request** (select+update ทีละวัน 7 วัน) → ใช้ `upsert` ครั้งเดียว + เพิ่ม `unique(week_id, day_index)` ป้องกันข้อมูลซ้ำ
6. **AI ตอบเป็น JSON แบบ parse ข้อความ** → ถ้า AI พิมพ์เกินมาจะพัง ควรใช้ Tool use/Structured output; `max_tokens: 2000` อาจตัด JSON ภาษาไทยขาด
7. **สัปดาห์ไม่ผูกกับวันที่จริง** — เพิ่ม `start_date` เพื่อดูย้อนหลังและคำนวณวันเหลือก่อนแข่งได้แม่นยำ
8. **ข้อมูลพื้นฐานผู้ใช้ไม่พอสำหรับคนอื่น** — ควรเก็บ อายุ, เพศ, Volume ปัจจุบัน, ประวัติบาดเจ็บ, Resting HR/Max HR (เพื่อทำ HR zone คู่กับ Pace zone)
9. **ไม่มีการจำกัดการใช้ AI ต่อคน** — ป้องกันค่าใช้จ่ายบานปลายเมื่อมีผู้ใช้หลายคน

### 🟢 ทำทีหลังได้

10. แยก `App.jsx` (1,000+ บรรทัด) เป็นไฟล์ตามหน้าจอ — แก้ง่าย, Claude ช่วยแก้ได้แม่นขึ้น
11. ทำเป็น PWA (ติดตั้งบนมือถือ) / เชื่อม Strava หรือ Garmin แทนการกรอกมือ
12. Dashboard สำหรับโค้ช (คุณ) ดูภาพรวมนักวิ่งทุกคน — แนวเดียวกับระบบติดตามผู้ป่วยหลังจำหน่าย

## ส่วนที่ 5 — ข้อเสนอการพัฒนา AI Coach (Design ใหม่)

```
[ข้อมูลผู้ใช้] → [Rule engine ในแอป]          → [AI (ฝั่ง server)]          → [Safety check]
                 คำนวณ: Phase จากวันแข่ง        ได้รับ: Coaching Playbook     ตรวจ red flag
                 Volume, 80/20 จริง,            ของคุณ + ตัวเลขที่คำนวณแล้ว   ก่อนแสดงผล
                 Down week, LR สูงสุด            ตีความ feel/notes + อธิบาย
```

1. **เขียน "Coaching Playbook"** (เอกสารแนวที่คุณสอน 1–2 หน้า) เก็บเป็นไฟล์ในโปรเจกต์ แล้วใส่ใน system prompt แทนชื่อสำนักต่างๆ — นี่คือขั้นที่สำคัญที่สุด และเป็นสิ่งที่ผมต้องการจากคุณ
2. ให้แอปคำนวณสิ่งที่วัดได้ แล้วส่ง "ผลคำนวณ" ให้ AI
3. ตัวอย่าง JSON ใช้ placeholder ไม่ใช่ค่าจริง และไม่ขัดกับกฎ
4. ตรวจ output ของ AI ซ้ำด้วยกฎ (เช่น Long run ไม่เกิน max, วันหนักไม่ติดกัน) ก่อนให้กด "ใช้โปรแกรม"
5. ทำชุดทดสอบ 5–10 เคส (เช่น "บาดเจ็บ", "RPE สูง 3 สัปดาห์", "เหลือ 2 สัปดาห์แข่ง") เพื่อประเมิน AI ทุกครั้งที่แก้ prompt — เปรียบได้กับการทำ Inter-rater reliability ของ Triage
